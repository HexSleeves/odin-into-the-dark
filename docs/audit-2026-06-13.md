# Into the Depths — Engine & Game Audit

_Date: 2026-06-13 · Scope: full `src/` (engine + game), `data/`, tooling · ~19.5K LOC src / 9K LOC test_

**Method.** 16 parallel evidence-grounded audits (11 subsystems + 5 cross-cutting lenses), each reading real source and citing `file:line`. Every Critical/High finding was then handed to an independent adversarial verifier that re-read the cited code and either confirmed, downgraded, or refuted it. **Priorities in this report are the _verified_ priorities, not the raw auditor claims.** Where the verifier overrode the auditor, that is noted — it is a deliberate credibility signal. 39 high/critical raised, 36 confirmed, 3 refuted/downgraded.

---

## Executive summary

This is a genuinely well-built hobby roguelike, not a prototype. The two-layer split (`src/engine/` backend-agnostic + `src/` game) is real and enforced: the engine has zero raylib imports outside `*_raylib.odin` files, the package dependency graph is acyclic (`core → {audio,ui,io,gen,render} → ai → gameplay → input`), the vtable backend abstraction is consistent and nil-safe, and the test runner is fast and headless. Memory safety is **better** than typical for the genre — entity death uses soft-delete + a single post-iteration `unordered_remove`, dynamic arrays store the heap allocator so `append` inside the per-frame arena is safe, and the documented "zero-init grid silently no-ops" trap is actually guarded.

The problems cluster in three places, in priority order:

1. **The persistence layer is the single biggest liability.** Saves are written non-atomically (`O_TRUNC` in place, no temp+rename, no fsync) over a 3.9 MB blob, the only save is deleted on load, the game is permadeath, there is no integrity check, and corrupt/tampered counts are used as loop bounds against fixed arrays while release builds compile with `-no-bounds-check`. One bad write or one corrupt file = lost run or out-of-bounds read.

2. **The safety net under all of this is an illusion.** CI runs `odin test src/ src/engine/`, but **no `*_test.odin` files live in `src/`** — they live in `test/` and are overlaid by the Python runner that CI does not call. So CI compiles the code and runs ~0 tests. The data-loss-critical save-migration chain has 6 branches and 1 test, and that one test only runs locally.

3. **The marketed core design pillar is hollow.** The README's "light is the central survival mechanic" is false in code: enemy detection is pure Manhattan `detection_radius` with no light input. Torches change only _your_ FOV and spawn distance, never your danger. The "darkness closes in" event is a pure annoyance with no risk/reward.

Everything else — a real but ABI-elidable by-value copy in grid accessors, a session-long `temp_allocator` leak, a type-unsafe service locator, ~374 hand-written re-export aliases that have already produced duplicated FOV code, a 253 KB `Game` struct (not the 112 KB the docs claim), and a brutal early-difficulty wall with shallow progression — is real debt but none of it is shipping broken today. Fix tier 1–3 first; they are cheap relative to their blast radius.

## Critical risks and blockers

### C1 — Save writes are non-atomic; a crash mid-write destroys the only save · **Critical** · _verifier confirmed, severity reinforced_

- **Issue.** `save_game_to_storage` builds the full ~3.9 MB buffer and calls `storage_manager_write` → `file_system_desktop` → `os.write_entire_file`, which opens with `O_TRUNC`, streams the bytes, and closes — no temp file, no atomic `rename`, no fsync. There is no `.bak`.
- **Why it matters.** The game is permadeath, and `load_game` **deletes the save on load** (`save_restore`/`save_query` ~:240). A crash, power loss, or disk-full during the write leaves a truncated file that is the only copy. Combined with C2, a partially-written file can also be silently accepted.
- **Evidence.** `src/io/save_write.odin:124-136` (single buf → `storage_manager_write`); `src/engine/storage_manager.odin:47-53` (passthrough); `src/io/file_system_desktop.odin:32-36` (`os.write_entire_file`, truncate defaults true); Odin stdlib `O_TRUNC + write + close`, no rename/fsync; `savegame.dat` measured 4,077,944 bytes; no `.bak`/rename anywhere in `src/`.
- **Fix.** Add a `rename` proc to the `Engine_File_System` vtable (it already has read/write/exists/remove at `src/engine/file_system.odin:9-22`), wired to `os.rename` on desktop and the IndexedDB/localStorage commit on web. Write to `path.tmp`, optionally fsync the temp fd, then atomically rename over `path`. Keep one rolling `savegame.dat.bak` before rename so a failed migration is recoverable.
- **Impact.** Eliminates the dominant data-loss path. Low effort, high payoff.

### C2 — Corrupt/tampered save counts used as loop bounds without clamping → OOB read · **High** · _verifier confirmed; held at High_

- **Issue.** `load_save_data` validates only magic + exact byte length, then `mem.copy`s raw bytes into `Save_Data`. The restore loops then iterate over file-controlled `enemy_count`/`item_count`/`room_count` (and per-floor counts) indexing **fixed** arrays (64/64/16/16).
- **Why it matters.** A corrupt or tampered save produces an out-of-bounds read. Release builds compile with `-no-bounds-check` (`justfile:47`), so it is silent UB rather than a panic. Nearby code already uses `min()` clamps (lines 112/120/125), proving the omission is an oversight, not a contract.
- **Evidence.** `src/io/save_migrations.odin:18-28`; restore loops `src/io/save_restore.odin:141/146/153`; `src/io/save_convert.odin:224-237`; capacities `src/io/save_format.odin:18-21`.
- **Fix.** After each `mem.copy`, clamp every count: `data.enemy_count = clamp(data.enemy_count, 0, MAX_SAVE_ENEMIES)` (and item/room/per-floor), or bound each loop `for i in 0 ..< min(data.enemy_count, MAX_SAVE_ENEMIES)`. Same in `save_to_floor`.
- **Impact.** Closes the only memory-safety bug found in the codebase. Trivial.

These two are the blockers. Everything below is debt, not a blocker.

## Engine architecture findings

The engine layer is the strongest part of the codebase. Findings here are mostly perf and dead-code, not correctness.

### E1 — `Tile_State_Manager` / `Bool_Grid_Manager` passed **by value** in per-cell read accessors · **Medium** · _auditor said High; verifier downgraded_
- **Issue.** `tile_state_at[_idx]`, `tile_state_visible/explored/light_level`, `bool_grid_manager_get/true_count` take the manager by value. `Tile_State_Manager` is ~49 KB (`[8192]Tile_State`), `Bool_Grid_Manager` ~8 KB. The matching set/clear procs already take pointers.
- **Why it matters.** These are per-tile FOV/render/save read primitives. By the language spec each call copies the whole backing array.
- **Verifier note.** Code matches exactly, **but** Odin's calling convention under `-o:speed` very likely passes these large non-mutating value params by hidden reference / elides the copy, so "massive memcpy" overstates the guaranteed cost. The fix is still correct and idiomatic.
- **Evidence.** `src/engine/tile_state_manager.odin:28/35/44/52/60`; `src/engine/bool_grid_manager.odin:22/48`; call sites `src/core/game_utils.odin:41/106/137`.
- **Fix.** Change the read accessors to take `^Tile_State_Manager` / `^Bool_Grid_Manager`, pass `&game.tile_states` / `&game.web_tiles` from the gcore wrappers. Keep nil guards.
- **Impact.** Removes any doubt about hot-path copies; aligns reads with the existing pointer-taking writes. Needs a profile to confirm real-world cost before treating as urgent.

### E2 — `Engine_Config.target_fps` silently ignored on the shipping (karl2d) path · **Medium**
- karl2d is injected for render/input/audio/texture/platform on **both** desktop and web; the raylib backends that honor `target_fps` are never exercised in production. Frame cap is whatever karl2d defaults to. `src/engine/engine.odin` config plumbing; `src/io/karl2d_backend.odin`.

### E3 — Platform vs app init failure indistinguishable; karl2d init always reports success · **Medium** · _auditor said High; verifier downgraded (diagnosability, not a crash)_
- `engine_init` returns a bare `bool` with no log at both the platform (`:231-233`) and app (`:240-242`) gates, and the karl2d wrapper discards `k2.init`'s `^State` return and unconditionally returns `true`. Asymmetric with `audio_init`, which does check `is_audio_ready`. Add a window-readiness check (`rl.IsWindowReady()` on raylib, a karl2d validity query) and log via the already-started diagnostics service before each `return false`; consider an error enum.

### E4 — Dead / aspirational engine code · **Medium → Low**
- `Energy_Actor` AP/quickness scheduler in `turn_manager.odin:37-70` with detailed Qud-style comments is **fully unused** — the real `Turn_Manager` is a bare `int` counter advanced once at `actions.odin:256`. (Note: the _game's_ energy/quickness scheduler in `src/ai` is real and tested; this is a second, dead engine-level one.) Also dead: `scene_update` (builds a throwaway Engine with stack-local services — and per S-app-ui findings, leaks 6 arena blocks), `camera_manager_abs`, `input_tick`, `reset_repeats`. Per the repo's "delete old paths by default" rule, delete or wire them.

### E5 — `Engine_State` holds self-referential pointers that break on copy · **Medium**
- `engine_init` sets `state.engine.services = &state.services` and binds the message log to `&state.engine.turn_manager`. Safe only because the two call sites never move the value (desktop stack-local `engine.odin:311`, web global `main_web_stub.odin:15`). Document the non-movable invariant, prefer `new(Engine_State)` for a stable address (mirroring the `Game` heap-alloc invariant), or rebind at the top of `engine_step`. Add a debug assert `state.engine.services == &state.services`.

### E6 — Fixed inline grid caps (8192) waste ~50%+ at the real map size (80×50 = 4000) · **Medium**
- Every `Game`/`Saved_Floor` copy carries the slack. Right-size the caps or make them depend on `MAP_CELLS`.

### E7 — "Manager-soup": Engine embeds 11 managers by value with parallel boilerplate accessors · **Low**
- Ownership/coupling is implicit. Not urgent; flag for when the manager count grows.

## Game architecture findings

### G1 — Service locator is type-unsafe by design · **Medium** · _auditor said High; verifier downgraded (latent, no active bug)_
- **Issue.** The 16-slot inline-arena registry returns a bare `rawptr`; every retrieval is a blind `cast(^Type)engine_services_get(...)` keyed on a hand-assigned `int` with no type tag. An id/type mismatch is silent UB.
- **Evidence.** `src/engine/engine_services.odin:14-19` (no typeid on register), `:169-175` (bare rawptr); blind casts at `game_services.odin:118/130/146/162/174/205` and `render/services.odin:10-108`; UI id 12 asserted as the same type from two packages.
- **Fix.** Add `type: typeid` to `Engine_Service_Registration`; register with `typeid_of(T)`; add a debug `engine_service_get_typed :: proc($T) -> ^T` that asserts the stored typeid. Costs one word per slot.

### G2 — Service-ID table defined three times, consumed split-brain · **Medium** · _verifier sharpened: it's THREE places, not two_
- IDs live in `core/service_ids.odin:5-16`, are **re-declared verbatim** in `game_services.odin:11-22`, and a third private `INPUT=7` in `input/common.odin:98`. Registration uses package-main constants; `render/services.odin` reads the gcore copies. They agree only by hand. Make `core/service_ids.odin` the sole source (ideally a distinct `enum Engine_Service_Id` so a dup/miss is a compile error), delete the others and alias.

### G3 — The ~374 re-export aliases form a distributed god-namespace and have already caused divergence · **Medium**
- Because Odin packages cannot import `package main` and leaf packages cannot see siblings, every package re-declares aliases in its `common.odin`. This is the **root cause** of the duplication class below (G4, M-arch findings): duplicated FOV, duplicated floor-snapshot helpers, hand-retyped content-ID literals, triple service-ID tables. Consolidate shared logic _down_ into `package core` (which everyone imports) rather than re-exporting _across_.

### G4 — FOV shadowcasting fully duplicated between `io` and `gameplay` · **Medium** · _verifier confirmed line-for-line copy_
- `io/save_common.odin:122-199` is a line-for-line copy of `gameplay/fov.odin:7-104` (because `gameplay` imports `io` but not vice-versa, and `save_restore.odin:227` needs FOV). `core` already owns `tile_at`/`tile_state_set`. Move shadowcasting into `src/core/fov.odin` as `gcore.compute_fov`; delete both copies; `gameplay/fov.odin` keeps only the debug-logging wrapper.

### G5 — Floor-snapshot lifecycle helpers defined twice · **Medium**
- `saved_floor_destroy` + `clear_visited_floors` are byte-identical in `gameio` (`save_common.odin:78/87`) and `gameplay` (`generation.odin:84/93`); `game_cleanup` exists in both (functionally identical, `gameio` also nils fields). `Saved_Floor` is in `core`. Promote all three into `package core` next to the struct; delete the copies. (Verifier corrected the auditor: `game_cleanup` is **not** byte-identical, so that part of the original claim was overstated.)

### G6 — `g_data` global content registry is dead · **Medium**
- Production always uses an injected `Content_Manager`; `g_data` + `data_load_all` survive only via nil-fallback branches that production never hits. Dead path — delete.

### G7 — The three "save" managers are NOT duplication · _resolved, no action_
- Verified clean facade chain: `engine.Storage_Manager` owns the byte/FS boundary, `core.Save_Manager` binds path+storage, `io.save_manager` adds game-aware save/load. The naming similarity is the only issue. One cleanup worth doing: `core/save_manager.odin` is a near-empty 19-line struct + `save_manager_save_exists` — verify it earns its place or fold it in.

### G8 — Map-generation ownership split across three packages with no orchestrator · **Low**
- `gameplay/generation.odin` dispatches into `src/gen/*` and overlaps conceptually. Acceptable now; consider a single `gen` entry point.

## Gameplay flow and direction findings

The content skeleton is surprisingly complete: 22 enemies across 6 depth-banded spawn tables, ~24 items in 3 loot tables, an energy/quickness turn system with weapon-speed tradeoffs (dagger 700 / pickaxe 1200 / greatsword 2100 action cost), 8 enemy abilities, status effects (poison/burn/freeze/web), a town hub with branching dialogue + quest, shrines/chests/merchants, treasure vaults, bosses at d5/10/12, per-tile audio/vfx feedback. The bones are strong. The weaknesses are the _risk model_ and _progression depth_ — these are **design-direction**, separate from the implementation bugs.

### D1 — The marketed central pillar (light = survival) has no effect on danger · **Medium (design-Critical)** · _verifier confirmed_
- **Issue.** README:5 and the Elder dialogue (`dialogue.json5:170`) sell light as the survival mechanic. In code, `enemy_update_awareness` (`enemy_turns.odin:74`) detects via pure Manhattan `dist <= detection_radius` with **no light input**. Light feeds only FOV (`fov.odin:11`) and spawn min-distance (`enemy_spawn.odin:53`). The "darkness closes in" light-drain event only shrinks vision — pure penalty, no risk/reward.
- **Why it matters.** This is the game's identity. Right now torches are free upside (see more) with no downside, so there is no decision.
- **Fix.** Make detection scale with the player's emitted light: if the player's light radius reaches the enemy, use full `detection_radius`; otherwise clamp to a small "hearing" radius (2–3). Now torches are genuine risk/reward and "darkness closes in" means "you trade safety for blindness." Add a stealth-in-dark line to help/Elder dialogue once true.
- **Impact.** Converts the headline feature from marketing into the actual core loop. This is the single highest-leverage _design_ change.

### D2 — Brutal early-game wall · **Medium** · _verifier confirmed data, tempered "spike-damage" wording_
- Player starts 25 HP / 5 ATK / **no armor** (`def=0`), facing d3-4 enemies with `flesh_brute` slam, `stone_thrower` (range 5), `toxic_spore`, `grasping_root` pull. Verifier: slam base is only 3 and ranged ~4 with 75–125% variance, so "spike damage" is somewhat overstated — it's a tuning problem, not a one-shot problem. Fix: give a starter armor piece (leather vest → def 1) or raise start HP to ~30; push `flesh_brute`/`grasping_root` from d3-4 to d5-6; gate `ranged_shoot` behind awareness/line-of-fire.

### D3 — Progression is shallow · **Medium** · _verifier confirmed_
- 3 flat stats, no levels/XP (no such field in `types.odin:53-65`), kills are inert (feed only score/HUD/particles), gear ceiling (+7/+2/+2) is reached in the d6+ table, shrines are the only stat source (and cost HP). Add a lightweight progression vector: reuse the `Shrine_Buff` enum as a level-up menu on milestone kills (no HP cost), or add a d8+ tier-3 equipment band (already on the README roadmap).

### D4 — No first-run onboarding · **Medium**
- Mechanics are discoverable only through a static help table. For a game with light/mining/crafting/status interplay, add contextual first-encounter prompts.

### D5 — Crafting + materials economy is thin and partly bypassed · **Medium**
- Recipes are a hardcoded literal array with magic string IDs (`core/recipes.odin`), bypassing the data-driven content system; the loop is underused.

### D6 — Merchant currency is broken/placeholder · **Medium** (impl bug, see also B-list)
- Depth-merchant `cost_id` is the `rusty_pickaxe` placeholder (`events.odin:187`); `inventory_count_item_type` scans only `game.inventory`, but the pickaxe lives in `equipped_weapon`, so cost reads 0 / buy fails. The **town** shop (iron/copper ore) works. One-line fix: set depth-merchant `cost_id` to a real currency.

### D7 — Quest/victory payoff is purely cosmetic · **Medium**
- Victory triggers on descending past `MAX_DEPTH` (`actions.odin:135`) — **not** on boss kill — and the reward is cosmetic. (This also defuses a separate auditor claim that boss-placement failure "gates victory": verifier confirmed it does not.) Give the dive a payoff (meta-unlock, score multiplier, run modifier).

### D8 — Combat lacks damage-state telegraphing / floating numbers · **Medium**; **`poison_cloud` ability has no effect** · several abilities are sprite-mapped without distinct AI · **Medium**.

## Performance and optimization findings

General posture is good for an 80×50 turn-based game: flat index grids with decent cache layout, Dijkstra + recursive-shadowcast FOV recomputed only on turn boundaries (not per frame), fixed particle pool, viewport-culled map render (~720 of 4000 tiles). **Profile before treating any of these as urgent** — none are confirmed bottlenecks, only structural costs.

### P1 — `context.temp_allocator` is never reset → session-long growth · **Medium** · _auditor said High; verifier downgraded (slow, bounded, no corruption)_
- `engine_step` swaps `context.allocator` to the per-frame arena (freed in `frame_manager_begin`) but **never touches `context.temp_allocator`**. HUD/UI `fmt.tprintf` (23 calls in `clay_hud` alone) ride the default temp arena, which has no `free_all` anywhere. It plateaus at the worst-frame string total (a few KB), so it's a leak, not per-frame churn.
- **Fix (trivial, safe).** In `engine_step` point `context.temp_allocator` at the frame arena too (`runtime.arena_allocator(&frame_manager.arena)`) so `tprintf` rides the arena already freed each frame. Clay stores raw pointers (`clay.odin:597-599`) but consumes them before the next frame's free, so this is safe — verify `EndLayout` happens in the same render call (it does).

### P2 — Floating minimap: O(tiles × entities) + 4050 Clay elements every frame when toggled · **Medium** · _auditor said High; verifier downgraded (toggle-gated, NPCs capped at 8)_
- `clay_minimap.odin` emits one `clay.UI` per 80×50 cell and calls linear-scan `enemy_at`/`npc_at` per cell, only while `ui.show_minimap`. Fix: invert the lookup — stamp enemy/npc cells into a `[MAP_WIDTH*MAP_HEIGHT]` scratch buffer once, read O(1) per cell; better, render the minimap as a single texture/image regenerated only when tiles change.

### P3 — Scores overlay reads + JSON-parses `scores.json` from disk **every render frame** · **Medium**
- `src/render/scores.odin`. Cache the parsed scores; refresh only on change. (Cheaper and clearer win than P1/P2.)

### P4 — `render_map` recomputes every visible tile color from scratch each frame, with duplicated color math · **Medium**
- Memoize per-`tile_state` colors; dedupe the color logic (it's duplicated across `render_map`/`render_color`). `render_map_dirty` is **written but never read** — wire it.

### P5 — `Tile` duplicates visibility/light already owned by `Tile_State_Manager` · **Medium** (also a data-model finding, see M1)
- Doubles the data and forces import/export copies. Drop the dead fields.

### P6 — Fixed-grid managers recompute validity (and `cell_count` = a w×h multiply) on every single access · **Medium**
- In the two tightest loops (FOV, render) and inside the Dijkstra BFS (~30–40K validity checks per pass for a grid that is provably constant for the whole pass). Hoist the validity/cell-count check out of the per-cell loop. Low-risk arithmetic removal.

### P7 — `trigger_enemy_rounds` recomputes the full Dijkstra BFS once per enemy round · **Medium**
- Multiplies cost for slow players (multiple enemy rounds per input). Cache the flow field per player-turn unless the map changed.

### P8 — **Zero profiling instrumentation exists** despite a `just profile` recipe (which only adds `-debug`) · **Medium**
- This is the meta-finding: you cannot prioritize P1–P7 without measurement. **Recommended instrumentation:** (a) a scoped timer macro writing per-system `time.tick_now()` deltas to the existing logger channels (`fov`, `enemy`, `gen`, `save`); (b) a `tracking_allocator` wrapped around the whole game loop in a debug build to count allocs/leaks per frame; (c) build `just profile` with `-o:speed -debug` + Spall/Tracy markers at `engine_step`, `process_enemy_turns`, `compute_dijkstra_map`, `compute_fov`, `render_game`, `save_game`. Add a debug overlay (toggle key) showing frame ms, alloc count, enemy count, BFS recompute count.

### P9 — Data layout: AoS enemy/item with linear-scan spatial queries · **Low**
- Fine at N≤30; will not scale. The cheap intermediate is the occupancy grid (`enemy_occupancy: [MAP_CELLS]i32` on `Game`) that also fixes A-perf (`enemy_at` O(N²)).

### P10 — Sprite mode does per-tile string-keyed hashmap lookups in the render inner loop · **Low**
- Resolve sprite indices once at load into an enum-indexed table.

## Reliability and maintainability findings

Memory safety is in good shape (see exec summary). The genuine gaps are concentrated at the persistence boundary and in silent error-swallowing.

### R1 — (= C2) Unclamped deserialized counts · **High**.
### R2 — Load deletes the save before the restored game is validated · **Medium**
- Failure mid-restore loses the save with no rollback. Validate the restored `Game` _before_ deleting (or before overwriting the `.bak` from C1).
### R3 — Migration size gate uses exact-equality on a fixed layout · **Medium**
- Any compiler/struct/padding drift silently rejects **all** old saves (`save_migrations.odin:18-28`). Brittle by construction; pairs badly with the absence of round-trip tests.
### R4 — NPC string pointers serialized raw into `Save_Floor` · **Medium (latent)**
- Latent-only today because NPCs exist solely on the always-regenerated surface. Re-intern via `Save_String` like enemies/items before NPCs can appear on dungeon floors.
### R5 — Web build has no filesystem; saves/loads/autosaves silently no-op · **Medium** · _auditor said High; verifier downgraded (secondary target, graceful)_
- `game_engine_config` never sets `config.file_system`, so on JS the default empty `Engine_File_System{}` makes storage nil-guards swallow everything — and autosave runs every `engine_step`. Implement a `#+build js` localStorage/IndexedDB backend, or gate the Continue/Save UI off on web and surface "saving unavailable."
### R6 — Silent error swallowing · **Medium (cluster)**
- Autosave return value discarded; `save_current_floor` failure on descent/ascent ignored (silent floor-state loss); `engine_services_register` silently overwrites on duplicate id. Propagate or at least log via the diagnostics service.
### R7 — Status effects persist across descend/ascend and into restored floors · **Medium**
- Poison/Burning/Frozen carry over unintentionally; several reset paths (`light_drain_timer`, equip/mining transient state) have gaps. Centralize floor-transition state reset.
### R8 — Module-global mutable state · **Medium/Low**
- `death_sound_played` (`src/input`) and the raylib font cache are package globals shared across games / not test-isolated. Move into `Game`/manager state.
### R9 — Latent glyph bug · **Medium**
- `rune(def.glyph[0])` reads only the first byte; breaks on any non-ASCII glyph (`core/data.odin`). Decode the first UTF-8 rune.
### R10 — Held movement keys produce diagonal moves in a cardinal-only roguelike · **Medium** · _verifier confirmed_
- `handle_input` (`playing_action.odin:44-60`) sets `dx` and `dy` from 4 independent `check_repeat` calls with no mutual exclusion; `is_walkable` has no corner-cut guard. Force one axis (`if dx != 0 && dy != 0 { dy = 0 }`); apply to `read_cardinal_press` for mining too.
### R11 — Escape hard-quits the process during play with no confirmation · **Medium**
- One stray Escape ends a permadeath run. Route Escape to a pause/confirm menu in the `Playing` state.

## Reliability of the safety net (tooling/CI)

The tooling is unusually mature (clean justfile, 335 `@(test)` procs across 6 packages, flag-matrix gate, GitHub Actions on two OSes, tag-triggered release producing Linux/macOS/web). But:

### T1 — CI runs a strictly weaker subset than `just verify`; green CI ≠ verify passes · **High** · _verifier sharpened: CI runs ~0 tests_

## Refuted / corrected by verification (do **not** treat as bugs)

The adversarial pass earned its cost here — these were raised as High and shot down or corrected:

1. **"Master-volume slider fights the music fade-lerp → volume flicker" — FALSE.** Both paths compute identical `g_music.volume * master_volume`; they converge, not clobber. The _real_ (Low) bug nearby: `g_game_config.music_volume` is never wired — music volume is hardcoded to `MUSIC_MASTER_VOLUME = 0.30`.
2. **"`generate_rooms` leaves the player on a wall at (0,0) when BSP places zero rooms" — unreachable in practice.** `generate_rooms` only runs at depth 1–2 with bounds floored at 52×34, and `BSP_MIN_LEAF_W/H` (12×9) guarantees every leaf clears `MIN_ROOM` 4×3, so ≥1 room always carves. Theoretical defensive gap, Low.
3. **"No load-time content validation → empty-slice crash" — FALSE.** All three `[0]` fallbacks in `content_manager.odin:60-72/84` are already `if len(...) > 0` guarded. The only real (Low) remnant: no _semantic_ validation/log on `#load`-embedded content, so a typo'd spawn id silently degrades to `[0]`.
4. **"`enemy_at` O(N²) per round" — real but Low, not High.** Runs once per player turn (not per frame), N capped ~15–30.
5. **"Boss-placement failure gates victory" — FALSE.** Victory is descend-past-`MAX_DEPTH`, never boss kill. The placement no-op is a quality issue, not a blocker.
6. **Vault stranding — real but High, not Critical.** Softlock requires a 20% trigger roll AND the randomly-sealed room to contain the descent/only corridor (depth ≥4, mixed/hybrid only; caves clear rooms). Still worth fixing (H-gen), just not Critical.
