# Architecture

> System structure, ownership boundaries, and data flow for Into the Depths.

## Overview

Into the Depths is a turn-based 2D roguelike with two architectural layers:

- **Engine layer** (`src/engine/`, `package engine`) — reusable, backend-agnostic managers
- **Game layer** (`src/`, `package main` + sub-packages) — game logic, scenes, rendering, data

## Engine Layer

### Design

Backend-agnostic. Every I/O boundary is a vtable struct (`{ctx: rawptr, fn_ptr, fn_ptr, ...}`):

- `Engine_File_System` — read/write/exists/remove
- `Engine_Input_Backend` — input polling
- `Engine_Audio_Backend` — audio playback
- `Engine_Render_Backend` — rendering primitives
- `Engine_Texture_Backend` — texture loading

Default implementations use OS/Raylib. Tests inject fake backends by constructing the struct directly.

### Managers

| Manager | Purpose | Backend-free? |
|---|---|---|
| `Scene_Manager` | Scene push/pop stack with enter/update/render/exit | Yes |
| `Turn_Manager` | Turn counter | Yes |
| `Storage_Manager` | Generic byte-level persistence via injected FS | Yes |
| `Camera_Manager` | Camera transform | Yes |
| `Particle_Manager` | Particle pool and update | Yes |
| `Message_Manager` | Typed in-engine events | Yes |
| `Audio_Manager` | Audio playback management | Yes |
| `Input_Manager` | Unified input with action mapping | Yes |
| `Sprite_Manager` | Sprite atlas and frame management | Yes |
| `Content_Manager` | Asset content loading | Yes (via FS) |
| `Config_Manager` | Runtime config and env vars | Yes |

### Services Registry

Game-layer singletons registered at init by `Engine_Service_Id` (typed `int`). Max 16 services. Stored in inline arena — no heap allocation.

Retrieval: `cast(^Type)eng.engine_services_get(engine.services, ID)`

Services: Content, Save, Sprite, Score, Input, UI

## Game Layer

### Sub-packages

| Package | Path | Role |
|---|---|---|
| `main` | `src/` | Entry point, app lifecycle, scene routing, alias shims |
| `gcore` | `src/core/` | Shared types, constants, content/save managers, inventory/equipment helpers |
| `gameplay` | `src/gameplay/` | Actions, items, mining, FOV, generation, status effects |
| `input` | `src/input/` | Input manager, key bindings, all input state handlers |
| `render` | `src/render/` | Clay UI, world rendering, sprites, particles |
| `audio` | `src/audio/` | Game audio and music |
| `gameio` | `src/io/` | Logging, save/storage, web assets, karl2d web backend |
| `ui` | `src/ui/` | UI text, theme constants, message helpers, UI manager |
| `ai` | `src/ai/` | Enemy turns, combat, abilities |
| `gen` | `src/gen/` | Map generation |

### App Lifecycle

```
main() → engine_run(config, services, &app)
  ├── Backend init (platform/audio/input/render/texture)
  ├── Manager init (texture, audio, storage, camera, turn, vfx, message, particle)
  ├── app.init → register services → load content (json5) → game_init → scene_init
  └── Loop:
      app.update → handle_global_input → scene_manager_update → scene callbacks
      app.render → scene_manager_render → active scene render callback
      [on exit] app.autosave
```

### Game_App Vtable

`init`, `update`, `render`, `shutdown`, `autosave` are function pointers + `rawptr state`. Game layer fills the struct; engine calls it.

### Scene System

`Game_State` enum maps 1:1 to `Game_Scene` enum. Each scene has `enter/update/render/exit` callbacks.

- `scene.odin` owns the mapping
- `engine.Scene_Manager` owns the lifecycle

## Data Flow

### Content Loading

1. `data/*.json5` (enemies, items, player, sprites)
2. `core:encoding/json` parses into Odin structs
3. `Data_Registry` stores all loaded data
4. `Content_Manager` wraps registry with typed accessors

### Save/Load

1. Binary save format using `Save_String` (fixed-size array + len)
2. Avoids heap pointers in serialized data
3. `Storage_Manager` with injected `Engine_File_System` handles I/O

### Rendering

**World rendering:** Game-layer `render_draw_*` helpers over `Engine_Render_Backend`
**UI rendering:** Clay immediate-mode → `clay_renderer.odin` → `Engine_Render_Backend`

Engine code never imports Clay.

## Boundaries

### Must Not Cross

- Engine layer → no Raylib imports
- Engine layer → no Clay imports
- Game layer → can use Raylib and Clay

### Generated/Vendor Files

- `src/vendor/clay/` — vendored Clay binding, do not edit
- `vendor/clay/` (top-level) — prebuilt platform libraries
- `build/` — generated by build system
